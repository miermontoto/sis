# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

Single-process monorepo: Hono serves API + SvelteKit SPA + background polling → SQLite.

```
Browser <──> Hono :3000
               ├── /api/*      → stats, auth, export, import
               ├── /auth/*     → OAuth login/callback
               ├── /*          → SvelteKit static SPA
               └── [internal]  → PollingService → SQLite (data/sis.db)
```

## Project structure

- `packages/api/` — Hono backend + polling + DB (TypeScript, tsx)
- `packages/web/` — SvelteKit 5 SPA with ECharts (adapter-static)
- `data/` — SQLite database (gitignored)
- Root scripts: `pnpm dev`, `pnpm build`, `pnpm start`

## Key commands

```bash
pnpm dev                    # start API with hot reload (tsx watch)
pnpm check                  # lint (oxlint) + typecheck both packages (api: tsc; web: svelte-check)
pnpm lint                   # oxlint only
pnpm build                  # build web → copy to api/static → build api
pnpm db:generate            # generate drizzle migrations after schema changes
docker compose up --build   # full containerized deployment
```

## Database

SQLite with WAL mode via better-sqlite3 + drizzle-orm. Schema in `packages/api/src/db/schema.ts`.
Tables: artists, albums, tracks, track_artists, listening_history, auth_tokens, polling_state.

## Key patterns

### Instancia en runtime (apk) — `lib/instance.ts`
El servidor es agnóstico de instancia (cada una con sus claves de spotify, el primer login es admin, el oauth móvil redirige al scheme `info.mier.sis://` que es de la **app**, no de la instancia). Lo que sí estaba atado era el cliente: el apk fijaba `VITE_API_BASE=https://sis.mier.info` en el build. Ya no existe: **todo origen de la api sale de `instanceOrigin()`** (`''` en web = mismo origen; en el apk la instancia elegida, en localStorage `sis:instance`) y `apiBase()` en `api/client.ts` es una función por lo mismo. No vuelvas a leer `import.meta.env.VITE_API_BASE` ni a exportar una constante con el origen.

El apk arranca **sin instancia** (decisión de Juan: picker en el primer arranque, la oficial es un atajo, no un default) y el layout manda a `/connect` (ruta bare) hasta que hay una; se cambia desde login y desde Settings → Connections. `normalizeInstanceUrl` (`utils/instance-url.ts`, con tests) **sólo acepta https**: spotify exige redirect https salvo loopback y la cookie lleva `secure`, así que una instancia http nunca completaría el login móvil. `probeInstance` valida contra `/api/version` (pública) y `switchInstance` **borra el cache entero**: las claves no llevan el origen y el mismo `user_id` existe en cualquier instancia.

`isForeignInstance()` (apk en una instancia que no es `OFFICIAL_INSTANCE`) apaga dos cosas: el **push** (los tokens fcm van atados al proyecto firebase del apk y ese server no puede firmar; el master queda deshabilitado con la explicación) y el **login con mier.info** (ver env vars). Los app links https siguen siendo sólo del dominio oficial (host en el manifest + assetlinks con la firma): los links de otra instancia abren en el browser. **No hay handshake de versión** (best effort, decisión de Juan): el bundle del apk sobrevive a la api, así que quitar un endpoint necesita una ventana de deprecación. Del lado de la api, lo que nombraba a sis.mier.info (user-agents de musicbrainz y setlist.fm) sale de `services/public-origin.ts`, derivado de `SPOTIFY_REDIRECT_URI`.

**El flujo móvil manda sobre la sesión del browser.** El custom tab comparte las cookies de chrome, así que si el móvil tenía una sesión web en sis.fm, los callbacks de last.fm y mier.info la veían y entraban en modo *vincular* (redirect a `/settings?…=linked` dentro del browser) en vez de entregar el código a la app; y como el intent-filter de app links casaba `/s` a secas (también `/settings`), a veces ese redirect abría la app en el login. `linkingSession()` en `routes/auth.ts` devuelve `null` con la cookie `sis_mobile`, y los prefijos del manifest llevan barra final (`/s/`, `/u/`, `/artist/`…). Spotify no tiene modo vincular y por eso nunca falló.

### API data flow
- `services/polling.ts` — setInterval-based polling (currently-playing 30s, recently-played 5m, artist metadata 24h)
- `services/ingestion.ts` — `upsertTrack()` upserts album/artists/track from Spotify data; `enrichArtistMetadata()` batch-fetches full artist details (images, genres) via `/v1/artists?ids=`
- `services/spotify-client.ts` — `spotifyFetch<T>()` handles auth headers, 401 token refresh, and 429 rate-limit retry
- `services/token-manager.ts` — stores tokens in DB, auto-refreshes before expiry
- `services/logger.ts` — `createLogger(scope)` for all API logging; no raw `console.*` in `packages/api` (the linter would let one through, so keep it by convention). Output is `[scope] message`, and `log.child(userId)` gives `[scope:12]` for per-user cycles. Chatty per-cycle lines belong at `debug`.

### Liked songs y pertenencia a playlists
`liked_tracks` + `liked_sync_state` son un **espejo local** de los liked songs de spotify (`services/liked-sync.ts`, 6h + lazy en el arranque diferido): `GET /now-playing/like/:id` (un tema, ya sólo para los apks publicados) y `GET /now-playing/liked?ids=` (el lote que pide la web) se responden en local (~1ms) en vez de con `/me/tracks/contains` (~100ms y una llamada a spotify por corazón pintado). Sin espejo para ese usuario se cae a spotify —en tandas de `LIKED_CONTAINS_MAX_IDS`— y se lanza el sync. `track_id` va **sin FK** a propósito: la biblioteca guardada incluye temas nunca ingestados y `foreign_keys = ON` obligaría a upsertear ese catálogo entero.

El sync explota que `/me/tracks` viene por fecha de guardado descendente: toda alta cae en la página 1 y toda baja mueve `total`, así que **el ciclo sin cambios cuesta UNA petición** en vez de paginar entero (36 páginas para 1780 temas). `liked_sync_state.total` es el que reportó **spotify**, no nuestro recuento: los temas que saltamos (ficheros locales) dejarían una discrepancia permanente y repaginaría cada ciclo. Por eso un like/unlike propio mueve el total ±1 además de la fila.

La pertenencia a playlists ya era local (`spotify_playlist_tracks`). `GET /now-playing/playlists?ids=` la devuelve **por lote** (`getTracksPlaylistPresence`, 3.6ms para 50 ids), con TODOS los ids preguntados —los vacíos incluidos— porque el cliente distingue "en ninguna" de "aún no lo sé". `idx_spt_track` es lo que la hace sargable: el único índice era `(playlist_id, track_id)` y preguntar por tema escaneaba la tabla. La ruta por id suelto sigue viva sólo para los apks publicados.

En el cliente hay **un solo store** (`stores/playlist-membership.svelte.ts`) para las dos pertenencias —playlists y liked— porque en spotify los liked songs son otra playlist más: lo comparten la tarjeta de now playing, el corazón del hero del detalle de tema (que además lo siembra con las playlists de su DTO) y las filas de las listas, así que darle al corazón o añadir a una playlist desde cualquiera de los tres se ve en los otros. `toggleLiked` es el **único camino de mutación** de liked que queda; `nowPlayingStore.isLiked` ya no tiene setter y el cliente no pregunta por un tema suelto (`api.trackLiked` es siempre por lote).

**Quien llame a `ensure()` dentro de un `$effect` lo hace dentro de `untrack`**: lee la misma pertenencia que escriben su respuesta y `seed()`. Sin él, el detalle de tema entraba en bucle infinito —cargar → sembrar → reejecutar el efecto → cargar— y colgaba la pestaña hasta que el renderer se caía.

La fila pinta **dos marcas distintas, no una suma**: el corazón (está en tus liked) y la cifra `+N` (está en N playlists). Estar en los liked no es estar en una playlist más, y el badge dejaría de decir si un tema te gusta. Las dos abren el `PlaylistPopover` en variante `inline`, que lleva **Liked Songs como primera fila** con su check/plus — la fila es el único sitio desde el que se quita y se pone, porque un click destructivo directo en una lista densa es fácil de dar sin querer. El popover pone esa fila sólo si el consumidor **no** trae `likeButton` propio (la tarjeta de now playing y el hero ya tienen corazón). Se monta **sólo en las filas con alguna pertenencia**: montarlo en todas sería un listener de documento por fila para no pintar nada. Lo gobierna el ajuste `showPlaylistBadges` (Detail lists → Playlist & liked badges, on por defecto; el prop de `TrackList` es `showLibraryBadges`), honrado por los detalles de artista y álbum.

### Artwork history (`album_covers` / `artist_images`)
Both tables are `(entity_id, image_url, source, observed_at)` with `UNIQUE(entity_id, image_url)` doing the dedup; `albums.image_url` / `artists.image_url` hold the *active* pick. Served on the detail endpoints (`covers` / `images`), edited through `PUT|POST /api/covers/album/:id` and `/api/covers/artist/:id`, rendered by the shared `ImagePicker.svelte`.

The two accrue differently. Album covers ride along for free: `upsertTrack()` inserts one per ingested play. Artist photos have no such source (recently-played carries no artist images), so `enrichArtistMetadata()` is a **rotating sweep** — `ORDER BY image_checked_at ASC LIMIT ARTIST_IMAGE_MAX_PER_CYCLE`, NULL first, whole catalog every ~10 days. Don't put an `image_url IS NULL` filter back on it: that asks for each artist once in its lifetime and freezes the history. Delisted artists (returned `null` inside the batch) still get `image_checked_at` stamped so they rotate out instead of clogging the queue head.

`artists.image_pinned` marks a manual pick so the sweep can't revert it. Albums have no equivalent — a manual cover *is* overwritten by the next ingested play of that album.

`albums.color` is a **manual `#rrggbb` pick** for everything that tints by album (ranking charts, album and track heroes). NULL = the color extracted client-side from the cover, which stays the default. `resolveEntityColor(color, imageUrl)` in `utils/color.ts` is the only place that decides that precedence — every consumer goes through it, never `extractColor` directly. Edited from the album page's `ImagePicker` **color tab** (native `<input type="color">` next to an "auto" swatch showing the extracted color; "Change color" in the hero menu opens it), saved by `PUT /api/covers/album/:id/color` (`null` resets). The pick travels inside every list/detail that carries the album (`TopAlbumItem.album`, `TrackInfo.album`, the detail DTOs), so the cover/color mutations clear those caches too. The tab also carries an **eyedropper** (`CoverEyedropper.svelte`): a palette of the cover's representative colors (`paletteFromPixels`, coarse quantization + minimum distance) and the cover drawn on a canvas whose pixel under the pointer previews on hover and saves on click. Pixel reading is `readImagePixels` (CORS-tainted images resolve null and the eyedropper hides itself), shared with `extractColor`, whose scoring is the pure `dominantFromPixels`: the **most common colorful color** (area × colorfulness over 4-bit buckets), so a cover's body red beats its brightest speck and a big neutral background loses to a colored logo; the original loudest-pixel rule survives only as the fallback when no bucket has color. Juan asked for it after noticing the palette's first swatch usually looked more like the album than the old auto.

`artists.background_url` is a **second, independent pick** over the same `artist_images` pool: the backdrop behind the artist hero (`DetailBackdrop.svelte`). NULL = fall back to `image_url`, so every artist gets a backdrop with no configuration. Setting it does *not* touch `image_url`/`image_pinned` (`PUT|POST /api/covers/artist/:id/background`); the shared `ImagePicker` grows a second tab when given `onSetBackground`. The treatment is a per-user setting, `artistBackdrop` (`off|blur|photo`, default `blur`) — Spotify serves no artist banner, only the square profile photo, which is why `blur` is the default.

### Relaciones de una entidad (`EntityRelations.svelte`)
Las dos intensidades viven en **una sola sección** del detalle (`relations`, registrada para artist/album/track en `detail-layout.ts`): **hard** = merges (`merge_rules`, con dirección) y **soft** = vínculos declarados entre artistas (`artist_relations`, simétricos, sin efecto en el tracking). Antes estaban partidas — los merges en un banner ámbar sobre el hero (`MergeBanners`) y las soft en chips del rail (`RelatedArtists`) — contando lo mismo en dos idiomas; los dos componentes están borrados, no los recrees.

El DTO lleva **una lista** `relations: EntityRelation[]` (`shared/relations.ts`) en los tres detalles; `mergedInto`/`mergedFrom` se derivan en cliente por `kind` (`alias` = esta página está dentro de otra, `absorbed` = la otra está dentro de ésta, `related` = soft). Con tres campos separados una página renderizaba unos y se olvidaba de otros. Cada fila es `TrackItem` + `MetricMeta` y sus acciones (make canonical / unmerge / remove relation / merge into) van en el **menú contextual**, como el resto de filas; el modal de merges y el de relaciones son el camino de teclado/táctil y los abre la cabecera de la sección (`Relate` / `Merge`). Tanto el menú contextual como el del hero llevan **una sola entrada**, `Relations`, y abre el modal de merges; las filas de la sección la omiten (`{ relations: false }`) porque ya traen las suyas. En artistas ese modal crece una tira de pestañas (`ModalTabs`, Merge/Relate) que salta al de relaciones con el mismo target y al revés, así que una entrada basta y mergear sigue alcanzable desde cualquier fila. Álbum y tema no tienen pestañas: no se "relacionan".

La regla del menú del hero es **una entrada por modal, no por pestaña ni por paso**: `Picture & background` y `Cover & color` abren el `ImagePicker`, que ya trae su propia tira de pestañas, y el `Auto-merge tracks` del álbum se fue porque el modal de merges siempre enseña su botón de scan. Dos entradas seguidas que abren la misma ventana son decir lo mismo dos veces.

Las cifras las da `getRelationStats` (queries/relations.ts), que cuenta cada id **como lo cuenta su propia página** (`[id, ...sus alias]`): así un `absorbed` reporta justo lo que aporta al grupo y un canónico su total, y las filas de la lista significan todas lo mismo. Los `CROSS JOIN` del arm de artista **fijan el orden del plan** y no se quitan: un CTE de `VALUES` no tiene estadísticas, así que con `JOIN` a secas el planner arranca por `listening_history` filtrando sólo por `user_id` y se come el historial entero (722ms medidos contra 14ms anclando en `rel` → `idx_ta_artist_position` → `idx_lh_user_track`). El `DISTINCT` por play es la otra mitad: una raíz y un alias suyo acreditados en el mismo track contarían ese play dos veces.

**`merge_rules` se filtra SIEMPRE por `user_id`**: una regla de merge es una decisión privada y sus escuchas son de quien la crea. `getEntityMergeInfo` no lo hacía y el detalle enseñaba los merges de los otros usuarios de la instancia (arreglado 2026-09-17). Para que no vuelva a pasar, `entityMergeJoin(type, userId)` exige el usuario (la rama sin filtro está borrada) y `resolvedEntityId`/`entityGroupCol` ya **no aceptan** un `userId`: era decorado —sólo nombran el alias— y hacía creer que la query quedaba acotada. Las únicas sentencias que tocan `merge_rules` sin filtrar son los barridos de borrado físico (`services/ingestion/merge-rules.ts` y el `is_merge_target` de `dedup.ts`), globales a propósito porque la fila de la entidad desaparece para todos y están comentadas como tal; dentro de ellas, **elegir a qué canónico se pliega un grupo sí va correlacionado por usuario** (`rewriteMergeRules` metía el grupo de B en el target elegido por A).

Que la página sea un alias lo dice además un `AliasBadge` pegado al nombre en el hero ("MERGED INTO X", con el nombre sin mayusculizar): la sección lo repite como fila, pero el rail se puede reordenar y esconder, y ese hecho explica la página entera (es lo que apaga records, ranking badges y chart stats).

### Álbumes lógicos (`album_collections` / `album_collection_members`)
Contenedor del usuario que agrega **álbumes enteros y temas sueltos** de un artista (una trilogía, una era, los singles de un año). Es la tercera intensidad de vínculo, y no es ninguna de las otras dos: un **merge** absorbe (la fuente pasa a ser un alias), una **relación soft** no toca el tracking, y una **colección** deja a sus miembros con su página y sus cifras intactas pero **los sustituye en los rankings** — top albums, charts, records y reports enseñan la colección, no sus partes.

**Una colección ES un álbum**: tiene su fila en `albums` con el id `collection:<N>`, y de ahí le vienen gratis la portada y su historial (`album_covers` + el `ImagePicker`), el color, la valoración, el buscador y **la vista de detalle entera** — `/album/collection:3` ES la página, no hay vista paralela; `/collection/:id` sólo redirige. `album_collections` guarda lo que un álbum no tiene (de quién es, de qué artista, notas) y `album_collection_members` la pertenencia.

La fila nace con **`artist_ids` y `release_date` a NULL** y eso no es descuido: es lo que mantiene lejos a los cuatro barridos de dedup de álbumes, que exigen tracks (`deduplicateAlbums`), créditos (`deduplicateEmptyAlbumShells`) o una fecha real (`deduplicateAlbumShells`). Aun así los tres llevan un `NOT LIKE 'collection:%'` explícito, porque depender de que sus condiciones no cambien es depender de una coincidencia — sin esa guarda, una colección llamada como un disco real ("Trilogy") desaparecería dentro de él. El único sitio que sí la pescaba es `enrichAlbumMetadata` (busca `artist_ids IS NULL`): preguntarle a spotify por `collection:3` es un 400. `isSpotifyId` (cliente) y `NON_SPOTIFY_ID_PREFIXES` (`services/ids.ts`) meten el prefijo en la familia de local:/import: — **pero no en `SYNTHETIC_ID_PREFIXES`**, que es la de los sweeps que fusionan sintéticos entre sí.

Lo que NO sale gratis de tener fila es todo lo que va del álbum a sus plays, porque **una colección no tiene temas propios**: cifras, serie, tracklist e historial salen del alcance de sus miembros (`getCollectionScope` + `scopeWhere`/`scopeDrive`), y el detalle de álbum despacha a `albumDetailForCollection`, que devuelve la MISMA forma (`AlbumDetail`) más `members`. `/stats/history` filtra por ese alcance con `collectionScope` (dos ejes en OR), que es lo que hace funcionar el rail de recent plays.

**Play en la colección**: spotify no tiene contexto para ella, así que el botón del hero manda su tracklist natural como `uris`. Ese orden es **cronológico** (`release_date` del disco, luego disco/pista), no el `position` de los miembros, que es el de inserción y no tiene UI (Conventional Weapons sonaría Five → One). Entran sólo temas de miembros directos (un álbum absorbido por merge repetiría los de su canónico) y sin sintéticos. Antes, `albumDetailForCollection` completa el tracklist de cada álbum miembro con `ensureFullAlbumTracks`, igual que el detalle de un álbum: en una colección de EPs suele faltar la mitad de los temas.

La capa que los sustituye en los rankings son dos LEFT JOIN metidos **dentro de `entityMergeJoin('album')`**, para que viajen siempre con `resolvedEntityId('album')`, que pasa a ser `COALESCE('collection:'||acm_track.collection_id, 'collection:'||acm_album.collection_id, mr_album.target_id, t.album_id)`. El miembro álbum se busca por el id **ya resuelto de merges** y el tema suelto gana sobre la colección de su álbum. Coste medido en top-albums all-time (349k plays): **377ms → 453ms**, y 453ms también con la tabla vacía: se paga el sondeo por fila. Las dos alternativas medidas están anotadas en `collectionMemberJoins`.

Las columnas del miembro son **`member_type`/`member_id`**, no `entity_*`: las queries de ranking alias su columna de grupo como `entity_id` y con ese nombre el `GROUP BY` se vuelve ambiguo (error real, igual que el `GROUP BY id` de los CTEs). `UNIQUE(user_id, member_type, member_id)` sostiene el invariante de **un miembro, UNA colección** — en dos, sus plays se contarían dos veces —, y las rutas lo traducen a un 409 que nombra la colección en conflicto.

**Sólo entra lo acreditado al artista de la colección** (422 si no): `isEligibleMember` reusa `artistCreditedAlbums` para los álbumes —la misma definición que decide qué discos salen en la página del artista, para que no haya uno que la página enseña y la colección rechaza— y el crédito en cualquier posición para los temas. Por eso el picker de miembros es `CollectionCandidatePicker` (candidatos del artista, con los ya tomados marcados) y no el `LibraryPicker` de búsqueda libre, y por eso el modal de "añadir a una colección" lista las de **cualquier** artista acreditado, no sólo el principal.

**Los miembros se guardan por su id CANÓNICO de merge** (`canonicalMemberId`): como el eje álbum resuelve merges *antes* de mirar la pertenencia, un alias como miembro no casa con ningún play y la colección rankeaba a cero mientras su propia página, que cuenta por el álbum crudo, enseñaba las escuchas. Por lo mismo `getCollectionRefs` canoniza lo que se le pregunta. Las cifras de la lista de miembros se cuentan por el álbum **crudo** del play y se reparten con `albumOwners` (cada álbum del alcance a un solo miembro), que si no un miembro mergeado dentro de otro marcaba 0 y las filas no sumaban el total.

Dos sitios del report necesitan trato aparte: las **décadas** se anclan al álbum REAL (`COALESCE(mr_album.target_id, t.album_id)`, que una colección no tiene fecha y sus plays se caían de la sección) y el **discovery** expande la colección a sus miembros (sin eso `noPlayBefore` no encontraba ninguno de sus tracks y TODA colección se estrenaba cada periodo).

Superficies: la página de álbum (con la sección `members`, registrada en `detail-layout` y pintada sólo cuando el id es una colección) y la línea de pertenencia en álbum y tema — en el álbum apaga además sus ranking badges y chart stats, que ahora son de la colección, igual que en un alias. **El detalle de artista NO tiene sección propia de colecciones**: ya salen en sus top albums, que es donde rankean, y una sección aparte era contar lo mismo dos veces (hubo una y está borrada, junto con `CollectionList`; el alta y el borrado viven en el `CollectionModal` que abre el menú del hero). Para distinguirlas en una lista de álbumes está `CollectionBadge`, un pill diminuto que se pinta solo con el id (`collection:N`) y no renderiza nada en una fila normal: va en `TrackItem` —que cubre de una vez dashboard, reports, records y los miembros— y a mano en las tres filas de álbum con markup propio (`/top`, `/charts` y los top albums del artista).

La entrada **"Add to collection" del menú contextual** de cualquier fila de álbum o tema sólo aparece si el artista de la fila TIENE alguna colección, y el menú se arma de forma **síncrona**, así que la respuesta no puede venir de una petición: sale de `stores/collections.svelte.ts`, un índice sin cifras (`GET /api/collections` → `getCollectionsIndex`) que se carga una vez en el layout y se invalida al crear o borrar. Cada fila del índice trae el **grupo de merge** del artista, porque el menú compara contra el id que tenga a mano, que puede ser un alias. El modal lo abre un store global (`collection-modal.svelte.ts`) con su host en el layout, igual que el de merges. Una fila que acaba sin ninguna acción no abre menú: un álbum lógico no se reproduce desde una fila (sólo desde su página, que arma la cola), no se mergea y no cabe en otra colección.

`collectionsStore.invalidate()` es **la única señal** de que una colección cambió, y la llaman TODAS las mutaciones (crear, borrar, renombrar, meter o sacar un miembro): refresca el índice del menú y sube un `changeVersion` que releen las vistas que enseñan álbumes (`/top`, `/charts`, dashboard, `/records`, `/reports/:g/:p`, artista, álbum y tema). Hacen falta las dos mitades: purgar el cache —que ya lo hace el fallback de `applyMutationInvalidation`— no sirve de nada si nadie vuelve a pedir, que es justo por lo que la lista desde la que acababas de añadir algo por el menú contextual se quedaba como estaba. Separar "refresca el índice" de "avisa a las vistas" en dos llamadas es la forma de olvidarse de una.

### Concert attendance log (`concerts` / `concert_songs`)
Per-user annotation on an artist, same contract as `album_ratings`: reads resolve the artist **merge group**, writes land on the visited id. `UNIQUE(user_id, artist_id, concert_date)` is what stops a show being logged twice, so the routes must translate it into a 409 — drizzle wraps the better-sqlite3 error, so the `SQLITE_CONSTRAINT_UNIQUE` code only appears down the `cause` chain (`isUniqueViolation` in `routes/concerts.ts`).

Surfaces: `/concert/:id` (the detail view — setlist rendered with the shared `TrackItem`, same row as every other list), a `concerts` section on the artist page (registered in `detail-layout.ts`), markers on the artist charts (`ChartEvent` gained `kind: 'concert'` + `href`), the global `/concerts` page (nav: Library), `concertsAttended`/`artistsSeenLive` on the profile card, and una sección **dentro del popover de `Accolades`** en los heroes de artista y tema (ticket verde en el trigger, lista de bolos debajo de los records). Hubo un `LiveBadge` aparte y se fusionó: dos botones idénticos uno al lado del otro competían sin decir cosas distintas. Lists link to the detail rather than expanding inline — one place renders a setlist.

Two records salen del log (al final del grupo **Other records** en `/records` — no tienen grupo propio: dos listas casi siempre vacías no sostienen una cabecera — y la medalla en la cabecera de la sección de directo del popover — no como fila suelta, que repetiría el título): `mostConcerts` (artistas más veces vistos, sin umbral — verlos una vez ya es el hecho que se rankea) y `mostHeardLive` (temas oídos en más bolos, `> 1` como el resto de records: con umbral 1 sería medio setlist empatado y ordenado al azar; con 11 bolos reales la lista sale vacía hasta que un tema se repita). No salen del historial, así que la marca de agua de la cache (`MAX(played_at)`) no se mueve al registrar un bolo: cada mutación de `routes/concerts.ts` llama a `invalidateRecordsCacheForUser`. En el cliente, las listas nuevas se leen con `?.` — una respuesta cacheada por la versión anterior no trae la clave y `.length` reventaba la página.

Every concert list row is the shared `ConcertRow.svelte` over `TrackItem` (variant `global`: artist photo + name, date in the meta column, since the list is grouped by year; variant `artist`: a day/month tile in the art slot and the venue as the name). Row actions (open, edit, remove, setlist.fm) live in the **right-click context menu**, like every other row in the app — no hover glyphs. `/concert/:id` is a detail route: `DetailBackdrop` + `.detail-hero-row` with the artist photo, `.stats-grid` of `.card.stat-card`, the setlist in `.track-list`, and a `.detail-rail` with notes and the artist's other shows. Its hero menu is `EntityActionsMenu` (edit / remove / setlist.fm) plus `.play-entity-btn` that plays the matched Spotify tracks in setlist order. Setlist rows open a context menu with the track's `entityContextActions` plus attribution actions; the visible "Attribute"/"Change" button is the keyboard/touch path. Unmatched songs mute the name, not the whole row, so that control stays legible. Stats cards must carry `.card` too — bare `.stat-card` renders as loose text. The track side is the reverse direction of the setlist match (`getTrackLiveConcerts` → `TrackDetail.liveConcerts`). The badge renders only when there *is* something to assert: its absence proves nothing, since a manually-logged concert has no setlist.

The setlist.fm search takes an optional `year`, **defaulting to the current year** — a long-touring artist runs to hundreds of shows (Bad Bunny: 521) and the common case is logging a gig you just went to. When that year has no setlists the filter drops itself back to all years, so an artist whose last tour predates it (Kendrick Lamar, last gig Dec 2025) doesn't open on an empty list.

The search chains `SETLISTFM_AUTO_PAGES` pages into **one continuous list**, with the rest behind an explicit "load more". Never go back to a prev/next pager: a list that stops at page 1's last row reads as missing data, and got reported as a bug twice ("missing Bad Bunny shows after Jun 11" — that was row 20 of 20).

setlist.fm models **every credit variant as its own artist entity** with its own MBID — 30 of them per artist ("J Balvin, Dua Lipa, Bad Bunny, Tainy", "Kendrick Lamar & SZA", "Myke Towers feat. Bad Bunny"…). Searching setlists by `artistName` is a substring match across all of them, so it pulled in other acts' concerts (two J Balvin shows filed under Bad Bunny). The route therefore resolves the entities first (`resolveAcceptedArtists`, cached 1h) and filters the results by an **MBID allowlist**. `classifySetlistfmBilling` in shared decides membership and is unit-tested against the real entity lists: the artist's own entity is `primary`; a shared bill they **lead** is `coheadline` and counts as theirs (Kendrick's Grand National Tour with SZA — 40 of his 60 most recent); appearing behind someone else, or behind a `feat.`/`presenta`/`x`, is `guest` and is dropped. Don't go back to unfiltered name search.

The route searches by the **visited** artist's name, never an arbitrary member of the merge group — picking one at random returned another act's tour wholesale (a merged alias, or the other half of a collab). The MBID may come from any group member, since it identifies the same person. The response echoes the `artistName` it searched with, and each row shows the **billed artist** when it differs from *that* (not from whatever name the client has on screen), compared **normalized** — Spotify's spelling vs setlist.fm's differ by case or stray spaces often enough that a raw `!==` labelled every row with the artist already in the header.

The page-chaining and the fallback live in `utils/setlist-search.ts`, **unit-tested** — three separate bugs shipped from having that logic inline in the component. The modal calls it behind a `loadSeq` token and inside `untrack`: `loadShows` reads `$state` it also writes, so an un-untracked call made the open-effect re-fire mid-load, before the async `loadedKey` guard was set, starting a second chain that appended to the same list (duplicated rows). Co-headline tours are credited to a separate setlist.fm entity ("Kendrick Lamar & SZA" — 40 of Kendrick's 60 most recent), and without that label those shows look identical to solo ones, so they read as missing too. The name search does return them; only the rendering hid them. Selecting a year re-searches on `change`; there is no per-keystroke search, since each one is a throttled third-party call. Its response is **not client-cached** (`NO_CACHE_PREFIXES` in `cache/config.ts`) because it carries `configured`, a server capability that no mutation invalidates — cached, the tab stayed disabled for a day after the key was set.

`services/setlistfm-client.ts` is credential-gated (`SETLISTFM_API_KEY`). The setlist search is **always by name, never by `artistMbid`**: on setlist.fm one MBID is one entity and the co-headline tour is a different one (Kendrick's MBID returned 14 shows for 2025; the name returns 54, 40 of them under "Kendrick Lamar & SZA"). `artists.mbid` is accreted evidence from the synthetic-track reconciler and has been wrong (Bad Bunny carried J Balvin's, so the MBID search returned J Balvin's tour, the allowlist emptied it and the modal said "no setlists"). It is only a **homonym tiebreaker** inside `acceptedSetlistfmArtists`, applied when it appears among the name-resolved entities and ignored otherwise. Its `eventDate` is `dd-MM-yyyy`, and `tape: true` songs are recorded intros, not performances (filtered out).

Attribution is **editable**: `PUT /api/concerts/:id/songs/:position` with `{trackId}` re-points a song, and `null` unlinks it. The auto-match is a name heuristic that fails predictably (titles repeated across records, live versions, songs it never found), so the detail view lets each row be corrected — the track must already exist, since attribution is evidence about the catalog, not a way to mint entities. The numeric route params are constrained (`/:id{[0-9]+}`) so they don't swallow `/artist/:id` or `/setlistfm/:id`.

Setlist songs are matched **read-only** against the library (`resolveSetlistSongs`): normalized name against the artist's catalog, then base-name (stripping `- Live` / `(Remastered)` suffixes) as a second pass, then the cover artist's catalog for covers. It must **never mint a synthetic track** — a setlist proves the band played something, not that the user heard it, so `track_id` NULL is the meaningful "not in your library" answer behind "you already knew 14 of 19".

`getConcertSongPlays` counts plays *before* the show date. It expands each song to its track merge group in a CTE **before** touching `listening_history`, so the filter is `lh.track_id = <id>` and hits `idx_lh_user_track_played_at` as a covering index; the direct `COALESCE(mr.target_id, lh.track_id) = cs.track_id` form is not sargable and degenerates into a full history scan per row.

Concert dates are **calendar dates**, not instants: format them with `formatCalendarDate` (UTC), never `formatShortDate`, or they render a day early west of Greenwich.

### Multi-source identity
Entity PKs stay in the spotify_id space (real IDs + `import:`/`local:` synthetics). `tracks.isrc/mbid`, `artists.mbid`, `albums.mbid` are resolution *evidence*, never keys (NULL = unqueried, `''` = queried without result). Resolution ladder in `history-import.ts`: isrc → mbid → name+primary artist (position 0 only) → mint synthetic; events accrete missing ids onto entities they resolve to. `ingestion/identity.ts` harvests ISRCs (Spotify `/tracks`, capped/cycle), MBIDs+ISRCs for synthetics (MusicBrainz, capped/cycle) and merges synthetics into real tracks sharing an id (`mergeTracksByIdentity`, via `reassignTrackRefs`). `listening_history.source` records play provenance (`spotify`|`lastfm`|`import`; NULL = pre-column rows).

The MusicBrainz search is Lucene, so the query is built by `mbRecordingQuery` (shared) as **quoted phrases**: unquoted, a `/` or `()` in the title is query syntax, and "One Way/Stolen Dance" returned "The Contract" at score 100 ("House Of Gold (Demo)" → "Doubt (demo)"). A hit is accepted only when its **title and artist credit both match ours** (`sameTitle` + normalized credit name, over the first `MB_SEARCH_LIMIT` results), never on score alone: a wrong MBID becomes a wrong ISRC and then a physical merge into the wrong track. The artist MBID is accreted from that same verified credit (the first credit is often another act).

**Gemelos exactos (mismo isrc + misma duración ±`TRACK_DEDUP_DURATION_TOLERANCE_MS`) se fusionan en duro, solos y sin pasar por la UI.** Spotify publica el mismo máster con un id por cada shell de álbum del lanzamiento ("Open Hearts" de *Hurry Up Tomorrow*: `0stJVU…` y `0sTBOp…`, mismo isrc, misma duración, un día de diferencia en `release_date`), así que cada play desde el gemelo acuñaba una fila propia. `resolveDuplicateTrackId()` (upsert.ts) redirige al id ya conocido **antes** de insertar — se llama también desde `pollCurrentlyPlaying` **antes** de comparar contra `polling_state`, porque dentro de `upsertTrack` el estado guardaría el canónico y `data.item.id` seguiría crudo, con `trackChanged` true en cada poll cerrando el play anterior una y otra vez. `mergeDuplicateTracksByIsrc()` (identity.ts) barre lo que ya existía o cuyo isrc llegó después del harvest, capado por `ISRC_DEDUP_MAX_PER_CYCLE` (cada merge cuesta ~27ms por el trigger FTS, ver abajo).

El **isrc suelto no identifica una grabación** y no basta para borrar una fila: en el catálogo hay isrcs de sello compartidos por temas distintos ("Saint Laurent" / "777", dos movimientos de la misma serenata). La duración es la otra mitad de la clave. El **nombre no entra**: el mismo máster se publica con créditos distintos ("CARNIVAL" / "CARNIVAL (feat. Rich The Kid, Playboi Carti)"). Por eso, cuando `upsertTrack` viene redirigido, **no pisa título, numeración ni créditos** del canónico (`reconcileTrackArtists` borraría los feats); sólo acreta isrc y refresca popularidad. Lo más flojo que eso (parecido de nombre, posición) sigue siendo una *propuesta* en el scan, nunca un merge duro.

`deduplicateTracks` (dedup.ts) sí era un merge duro por **nombre + artista de posición 0**, la señal más floja del proyecto colgando de la acción más destructiva, y por ahí se comió versiones distintas: el single de "Runaway" (`50HCj9kEXIonBwRLXFWCr8`, 5:39, isrc `USUM71024424`) desapareció dentro del corte de MBDTF (`3DK6m7It6Pw857FcQftMds`, 9:07, `USUM71027402`) con sus 73 plays. Ahora pasa por `isSameRecording`: duración ±`TRACK_DEDUP_DURATION_TOLERANCE_MS` **contra el canónico** (no en cadena, la tolerancia no es transitiva) y, si ambos traen isrc y difieren, son dos grabaciones registradas distintas. Duración `<= 0` (pendiente de enrichment) se aplaza al siguiente ciclo en vez de mergear a ciegas. No le quites el guard: el barrido corre cada ciclo de polling, así que la fila desaparece en menos de media hora y lo único que queda es la huella forense.

**La huella de una versión absorbida es un `duration_played_ms` constante que no es la duración del track** (un valor repetido a la milésima 73 veces es una duración de track, no un hábito de escucha), y tiene **dos causas distintas que hay que separar antes de tocar nada**: (a) la fila absorbida de verdad, o (b) `tracks.duration_ms` obsoleto, donde los plays siempre estuvieron bien y el que miente es nuestro dato. Las distingue `GET /v1/tracks?ids=` sobre el **mismo id**: si spotify devuelve la duración del fantasma, es (b). En el barrido de 2026-09-16 salieron 60 huellas / 1017 plays → 19 duraciones obsoletas corregidas, 626 plays devueltos a 26 grabaciones (14 filas recreadas desde spotify), 12 sin destino identificable. El nombre a secas no basta para encontrar el destino: la clave es **duración exacta + artista de posición 0**, y se prefiere una fila que ya exista antes que crear otra.

Ojo con el sentido del merge, que no siempre es "el single cae en el álbum": *TRON: Legacy Reconfigured* tiene un segundo lanzamiento (`4LTuhh4qpSn8uUrjhiWTj3`) cuyos remixes van con **nombre pelado** ("Fall", "The Son of Flynn"), así que ahí lo que se comió el cue de 1:22 del score fue el remix de 3:55. Las filas "- Remixed by X" sobrevivieron justo porque su nombre no colisiona.

`reassignTrackRefs` es la lista completa de referencias a un `track_id`, y **ahí se añade cualquier tabla nueva**: nada lo obliga (no hay FK) y la referencia rota no da error, sólo desaparece de donde se veía. Faltaban dos: `concert_songs` (la atribución de setlists, evidencia del usuario) y `polling_state.last_currently_playing_track_id` — sin ésta, fusionar el track que sonaba vaciaba el now playing a mitad de canción (`now-playing.ts` devuelve `playing:false` si la fila no está) y sacaba al usuario del feed social. `reassignAlbumRefs` es su equivalente y el cuerpo común de los cuatro dedup de álbum.

Del lado del álbum, `deduplicateAlbumShells` lleva `release_date` en su clave y **no puede soltarla** (fusionaría lanzamientos distintos), así que los dos shells de *Hurry Up Tomorrow* nunca colapsaban. `deduplicateEmptyAlbumShells` cubre el hueco con la única excepción segura: un shell **sin ningún track ingestado** no es un lanzamiento que preservar (una deluxe y su estándar tienen tracks las dos), así que se absorbe en la hermana poblada del mismo nombre/tipo/artista ignorando la fecha.

El índice FTS se purga **en batch** (`pruneOrphanSearchIndex`), nunca por merge: `entity_id` es `UNINDEXED` en fts5, así que un `DELETE` sin `MATCH` recorre las 89k filas (24ms) — el trigger `fts_track_artists_ad` ya paga ese peaje una vez por merge. Por la misma razón, un subquery correlado sobre `LOWER(name)` en álbumes es O(n²) (13s): `deduplicateEmptyAlbumShells` hace una pasada plana y agrupa en JS.

**`local:` e `import:` son UN espacio, no dos.** `SYNTHETIC_ID_PREFIXES` (ids.ts) ya lo decía, pero cada lookup filtraba su prefijo a mano y el mismo disco vivía partido en dos filas con el **mismo cuerpo de hash y distinto prefijo** — los dos caminos acuñan el álbum como `syntheticId(prefix, artista, álbum)`, así que `import:65c4c03f7adeaab7` y `local:65c4c03f7adeaab7` son "2008 - Louis Vuitton Runway Show Mix" por duplicado. `history-import.ts` sí cruzaba la frontera (su `CASE` ordena real > import > local); `resolveLocalFileIds` y `deduplicateLocalAlbums` no, así que un archivo local que ya existía como `import:` acuñaba fila nueva y nada volvía a juntarlas (8 álbumes y 13 tracks en prod, 2026-09-16). El predicado y el orden salen ahora de `syntheticIdPredicate`/`syntheticPreference` (ids.ts), derivados de la lista de prefijos: **no vuelvas a escribir `LIKE 'local:%'` suelto en un sweep**. `import:` gana como canónico porque es la fila con el historial largo.

`deduplicateSyntheticTracks` cubre los que viven en álbumes distintos (el tema en el álbum real y en su gemelo local). Su clave lleva el **nombre del álbum**, y eso no es opcional: sin él se comía "Kitchen Sink" de *Regional At Best* (334s) con la de *Vessel* (331s) y "Shy Away / I'm Not Okay (Live)" de *Hometown Show* (247s) con la de 242s — mismo título y dentro de la tolerancia, pero son grabaciones distintas. **Nunca fusiona un sintético dentro de un id real de spotify**: eso es lo que vació álbumes `local:` en agosto de 2026, y para `import:` → real ya está `mergeImportTracks`.

**Tracks on `local:` albums are excluded from identity entirely** (`identityCandidate` in identity.ts: no MB query, no merge). A local album is a user container (setlist, bootleg, compilation) whose tracks carry the studio title and the real artist, so identity evidence drains it into the studio tracks. It happened in Aug 2026: 23 tracks across 8 local albums (a festival recording went 20 → 9), restored from the weekly backup on 2026-09-03 with `isrc`/`mbid` set to `''` on purpose.

### Plays duplicados entre filas de track distintas (`cleanCrossTrackDuplicates`)
`cleanDuplicatePlays` y `cleanBasicExtendedDuplicates` cruzan las dos filas por **track_id idéntico**, así que el mismo play importado dos veces que resolvió a DOS filas distintas les era invisible y sobrevivía a todos los barridos. Pasa porque el export Basic trae el título pelado y el Extended el de la edición real: "Enter Sandman" (estudio) y "Enter Sandman - Live" (S&M2) se llevan una copia cada uno, igual que "Take My Breath" (Dawn FM, 5:39) y "Take My Breath - Single Version" (3:40) — spotify renombró el single cuando salió el álbum, así que las filas de 2021 del export traen el nombre pelado y la escalera de `history-import.ts` las mandó al corte de álbum, que **aún no existía**.

**`played_at` no significa lo mismo en todas las fuentes.** Medido sobre pares consecutivos con duración en los dos: `spotify` y el import antiguo (`source` NULL) marcan el **FIN** (183.339 pares contra 1.314), pero las filas `source='import'` marcan el **INICIO** (85 contra 6). `playWindow` en dedup.ts es quien lo resuelve; no vuelvas a asumir una única semántica. Asumirlo invalidaba la prueba en 24 filas del barrido (que se sostenían por la vía del mismo instante) y dejaba 67 duplicados reales sin detectar. La prueba del **mismo instante** —dos filas del mismo tema a menos de 2s— vale por sí sola y no depende de ninguna interpretación.

**El nombre no decide, sólo acota; quien decide es el reloj.** Una fila sin `duration_played_ms`, si fuese una escucha real, ocuparía `[marca - duración del track, marca]`; si ese intervalo pisa `PLAY_OVERLAP_PROOF_S` (30s) el de un play MEDIDO, las dos no pudieron sonar a la vez y la fantasma es la que no trae medición. Esa prueba no mira títulos y cubrió el 89% de los candidatos (1258 de 1414). El gemelo por nombre base (mismo artista de posición 0, `playBaseName`) se exige ADEMÁS, para no tocar filas cuyo solape venga de otra cosa. Nunca borres por parecido de nombre a secas: es la operación que se comió el single de "Runaway".

Ojo con el patrón de **desfase** (la Basic una duración del gemelo por delante de la Extended): por sí solo es indistinguible de escuchar A y luego B seguidos, y son 679 de los 829 candidatos por nombre. Sólo la prueba del reloj lo separa. La categoría que la prueba NO cubre es la de **duraciones rotas** (un track de 11s, "Monster" de Michael Jackson): la ventana implícita sale minúscula y no solapa con nada, así que esos quedan fuera a propósito.

Barrido de 2026-09-16: 72 plays de "Take My Breath" (más 4 reapuntados al single) y 1258 cross-track, ~7h y ~50h de tiempo fantasma. Backups en el contenedor: `sis-pretmb-20260916.db` y `sis-prexdup-20260916.db`. **"El play es anterior a la fecha de su álbum" NO es por sí solo prueba de nada**: salieron 17.804, y la mayoría son shells de aniversario o singles de preestreno con el mismo máster. El cluster de *Scaled And Icy (Livestream Version)* de Twenty One Pilots es un falso positivo — los cortes de estudio tienen 182-216 plays en la misma ventana, así que las escuchas del directo son reales.

### Qué álbumes son "del artista" (`artistCreditedAlbums`, helpers.ts)
La lista de álbumes del detalle de artista y sus marcadores de release (`getArtistTopAlbums` / `getArtistReleases`) salen los dos de este helper, que une **tres** vías:

1. **Crédito a nivel de álbum** (`albums.artist_ids`, en cualquier posición): un disco a dos nombres es de los dos, así que OASIS sale en Bad Bunny y Watch The Throne en Kanye. El crédito a nivel de track **no** vale por sí solo: bastaba un tema suyo para colar la recopilación entera (8 Mile, SHADYXV, ED REC Vol.X, Black Panther, y *Curtain Call* en la de JAŸ-Z porque lidera un bonus track).
2. **Primario desconocido + mayoría de lo ingestado.** `artist_ids` tiene **tres** estados: array real, `NULL` (sin enriquecer, 8386 álbumes con plays) y `'[]'` (los sintéticos `local:`/`import:`). `json_extract(...,'$[0]') IS NULL` cubre los dos últimos de una vez; escrito como `artist_ids IS NULL` se dejaba fuera justo los mixtapes del usuario. Se exige **mayoría**: un invitado liderando un corte es normal en un disco propio (*Detroit 2*, 20 de 21), pero en una banda sonora nadie pasa de la mitad (*8 Mile*, 3 de 13).
3. **Créditos conocidos que NO lo nombran, pero lidera la mayoría de los temas PUBLICADOS.** Spotify acredita el disco a otra entidad y aun así el artista firma casi todo: los dos álbumes de **Token** (12 de 17 y 15 de 17, **2631 plays** que desaparecieron de su página al soltar la vía del track), los de Kavinsky, las OST de juegos (Masakazu Sugimori, 24 de 34), *Straight Outta Compton*. Aquí se contradice el dato de Spotify, así que la prueba es más dura que en (2): la mayoría se mide contra **`total_tracks`**, no contra lo ingestado. Con lo ingestado, un único tema nuestro de un recopilatorio da un "1 de 1" que pasa como mayoría y vuelven a colarse el DJ mix (*Kitsuné Boombox*), la banda sonora (*The Harder They Fall*) y *For The Throne*. Filtrar por `album_type != 'compilation'` NO basta: esos tres vienen tipados como `album`.

Lo que la mayoría no puede distinguir es una recopilación de la que sólo se ingestó **un** tema, el suyo: se arregla solo cuando el enrichment rellena `artist_ids`. El arm de respaldo **ancla primero en el artista** (subquery por `idx_ta_artist_position`) y agrupa después: agrupar de entrada todos los álbumes candidatos son ~11k por página y cuesta 80ms en vez de 22ms, trabajo que ni depende del artista.

### Stats endpoints (`routes/stats.ts`)
All top-* endpoints accept `?range=` (from `TIME_RANGES` in constants.ts), `?limit=`, and `?sort=time|plays`. The `sort` param controls SQL ORDER BY (sum of duration vs count). All return both `playCount` and `totalMs`.

`TIME_RANGES` uses sentinel values: `0` = all time (no filter), `-1` = thisYear (Jan 1 UTC of current year).

### Records cache y accolades (`services/records-cache.ts`)
Los records de un usuario se hornean enteros (los tres tipos, limit 50) en **una entrada en memoria** por `userId:weekStart:sort:unique`, y de esa misma entrada salen los accolades del hero (`getEntityAccolades` la busca por prefijo de usuario). El horneado cuesta ~12s de escaneo del historial, lo lanza el arranque diferido del usuario y lo repite el tick de polling cada 6h.

**Una lista vacía nunca puede ser la respuesta a una cache fría.** `[]` no se distingue de "esta entidad no tiene records", y el cliente lo cachea una hora por entidad (`/stats/accolades/`, 1h fresh / 7d stale), así que la mentira sobrevive al servidor: el badge desaparecía de artistas, álbumes y temas. Por eso una lectura en frío **espera al horneado** (deduplicado por usuario: el detalle pide los tres tipos a la vez y el arranque diferido lanza el suyo). `/records` no lo enseñaba porque su ruta cae a `dbRead('getRecords', …)` cuando falla la cache; la de accolades no tenía salida.

La cache se queda fría a menudo: cada deploy recrea el contenedor, y `invalidateRecordsCacheForUser` la borra desde las cinco mutaciones de colección (`invalidateDerived`) y las cuatro de bolo **sin rehornear nada** — `triggerDeferredStartup` es de una sola vez por proceso, así que sin la espera el hueco duraba hasta las 6h del siguiente tick. Esas invalidaciones existen porque la marca de agua del horneado es `MAX(played_at)`, que ni una colección ni un bolo mueven; por lo mismo suben la **generación** del usuario, y un horneado en vuelo que la vea cambiada descarta su resultado y recomputa en vez de guardar datos pre-mutación otras 6h.

### Chart peaks (streaming)
`/stats/charts/peaks` (batch JSON) and `/stats/charts/peaks/stream` (NDJSON, one line per entity) return the same stats. Both drive `services/chart-peaks.ts`: the per-period `ROW_NUMBER()` scan is split into one-calendar-year `played_at` windows (work-preserving, since the ranking is partitioned by period, and index-friendly via `(user_id, played_at)`), walked newest → oldest, closing each entity once the scan passes its own first play. Year cut points are `Jan 1 + weekStart shift`, which never splits a period label. The batch endpoint stays as the client's fallback (shipped APKs, proxies that eat chunked responses).

Writing any streaming route: `dbRead` runs **synchronously on the main thread in dev** (worker pool only in prod), so the handler must `await setImmediate` between chunks or nothing flushes until it returns. Set `X-Accel-Buffering: no` so nginx doesn't buffer it in production.

### Periodic reports (`/reports`)
Last.fm-style **weekly / monthly / yearly reports**, only for **closed periods**. A report shares the period key with the charts (`2026-W34`, `2026-08`, `2025`, honouring `weekStart`), so it covers exactly the plays the chart of that period ranks and the two link to each other. The period model lives in **shared** (`periods.ts`: `periodForDate`, `periodBounds`, `adjacentPeriod`, `isClosedPeriod`), unit-tested in `web/src/lib/utils/period-bounds.test.ts` against SQLite's own `strftime` via `node:sqlite` (so the label math can't drift from `periodExpr`): a Monday January 1st is already **W01**, week 53 exists in some years, and the week label splits at New Year. Server and client both decide "closed" with that module in **UTC**; the client's `computeCurrentPeriod` (charts banner) uses the local calendar day instead, which differs for a couple of hours around the boundary west/east of UTC.

`GET /api/stats/report?granularity&period&weekStart&sort&tz` → one `ReportResponse` (`shared/reports.ts`) from `db/queries/reports.ts`. Plays are filtered by **`[start, end)` bounds** (indexed on `(user_id, played_at)`), never with `periodExpr() = period` like the charts: that is a full history scan per query and a report runs a dozen. Days and weekdays are UTC buckets like the charts; only the **hour clock** is shifted to the client's `tz` (minutes), and it is the one section recomputed live on top of the cache. Discovery ("new to you") is a `NOT EXISTS` probe per period entity over `(user_id, track_id, played_at)`, not a `MIN(played_at)` over the whole history. Album discovery deliberately ignores track-merge sources (the merge_rules × tracks join per album cost 5s on a year). `MILESTONE_THRESHOLDS` from the notifications doubles as the milestone ladder. The top lists carry the **same NEW / RE badges as the charts page**: rank change against the previous period's top 200, and for what wasn't there `getChartPeaks` decides re-entry (charted before) vs new (never charted) — ~1-2 s per entity type, absorbed by the bake. Without it every returning entity read as NEW.

Reports are **pre-baked** (`services/report-cache.ts`, same idea as records): keyed by user + granularity + period + weekStart + sort, `REPORT_CACHE_TTL_MS` (1 day) with stale-while-revalidate, the latest closed week/month/year of each user baked at deferred startup and on an hourly tick (`REPORT_WARM_INTERVAL_MS`), older periods memoized on first request, `REPORT_CACHE_MAX_PER_USER` entries. Manual scrobbles, history deletes and imports call `invalidateReportCacheForUser`; late scrobbles and merges are absorbed by the TTL on purpose. The weekly `chart_closing` push deep-links to `/reports/week/<period>`.

Two SQL gotchas found here: better-sqlite3 binds JS numbers as **REAL**, so an integer-division constant must go through `sql.raw` (`/ ${10}` made every year its own decade); and in a CTE `GROUP BY id` resolves against `merge_rules.id` / `listening_history.id` before the alias (ambiguous column), so those CTEs group by **ordinal**.

UI: `/reports` index (last closed week/month/year + closed-period history from `/stats/charts/periods`) and `/reports/[granularity]/[period]` (hero with `DetailBackdrop` of the #1 artist, deltas vs the previous period, #1 card per column via `ReportTopCard` with the rest as `TrackItem` rows, `ReportPolar` for the clock/weekdays, `ReportBars` for genres and decades, one `ReportTopCard` per top new artist/album/track, month strip and milestones for years). Not shipped on purpose (phase 2 candidates): artist map (no country data; MBIDs on 3% of artists), share link / PNG export, month and year closing pushes.

### Refresco al registrarse un play (`stores/play-updates.svelte.ts`)
Dos señales, y no son intercambiables. **optimistic** la emite el cliente al ver cambiar el track sonando: las vistas de ranking suman el play a sus filas y reordenan sin tocar la red. **confirmed** son los plays que el servidor dice que ya están en `listening_history` — `/now-playing` acepta `?since=<marca>` y devuelve `landedPlays` (`readHistoryTail`); sólo entonces una relectura devuelve la verdad, y releer antes recachearía las cifras viejas durante el TTL entero (1h en los detalles), que es justo el fallo que se evita. Los detalles (clave de cache estrecha, un request) relen con la confirmada; los tops se quedan en la optimista y dejan que el TTL reconcilie. **Ningún consumidor SUMA sobre `confirmed`** — todos relen —, así que un play que llegue por las dos no se cuenta dos veces.

El umbral del play optimista es el **progreso del track** (`progressMsAt`), nunca el tiempo que lleva el cliente mirándolo: con el reloj de observación, abrir la app a mitad de canción no emitía nada y el play aterrizaba sin que ninguna vista se enterara. Y la confirmación **la manda el servidor**, no se infiere de correlacionar la marca de agua con lo emitido aquí: un repeat-one, la app en segundo plano, otro dispositivo o un scrobble de last.fm/listenbrainz registran plays sin que la tarjeta de now-playing cambie nunca. No vuelvas a colgar el refresco de haber visto el corte.

Sin suscribir a propósito (endpoints caros, TTL propio): `/records`, `/insights`, `/trends`, perfil y playlists. `/history` y las recent plays del dashboard tienen su propio poll de 15s.

Lo que ve el usuario cuando algo cambia en vivo son **dos marcas transitorias** de `stat-flash.svelte.ts`, por id de entidad y con el mismo temporizador (3 × 350 ms, que tiene que cuadrar con `.stat-flash` de app.css y `.rank-change--live`): `flash` = la cifra ha cambiado, `move` = la fila ha cambiado de puesto. Son independientes — sumar un play sin adelantar a nadie es sólo flash, y ser adelantada es sólo move. La flecha va en **toda** fila que cambió de puesto (`rankMoves`, pura y con tests), no sólo en la que sumó el play, y mientras dura tapa al delta del lookback: es lo que acaba de pasar. Parpadea sobre la **opacidad**, nunca con `.stat-flash`, que tira a verde a media animación y teñiría de verde una flecha de bajada.

La columna de puesto de cualquier fila de ranking es **`RankCell.svelte`** (número + badge). No la vuelvas a montar a mano: había tres copias, y el badge en vivo obliga a que la columna aparezca aunque la vista no pinte deltas de lookback. `/charts` conserva la suya porque su columna tiene estilos propios (`chart-rank`).

### Preferencias de usuario
Una preferencia nueva se declara en **cuatro** sitios y los cuatro tienen que coincidir: `VALID_KEYS` + `DEFAULTS` (`api/routes/settings.ts`), `SettingsData` + `SETTINGS_DEFAULTS` (`web/lib/api/settings.ts`), su `stringSetting`/`boolSetting` y el re-export de `lib/api/index.ts`. `VALID_KEYS` es una **allowlist muda**: la clave que falta ahí se acepta en el PUT, se tira, y `loadSettings` la devuelve al default en la siguiente carga (le pasó a `sessionTrackingDisplay` hasta 2026-09-11). ## Scrobble ingestion (ListenBrainz-compatible)

`GET /1/validate-token` + `POST /1/submit-listens` (`single`|`import`|`playing_now`), mounted at the site root *outside* the session gate — auth is a per-user token (`listen_tokens`, managed via `/api/listen-token` and Settings → Connections → Scrobblers). Clients (Pano Scrobbler, Web Scrobbler, Navidrome…) point their custom ListenBrainz server URL at the site origin. Listens map to `ListenEvent` → `importListenEvents()` (`history-import.ts`), which runs the identity ladder — a `spotify_id` URL in `additional_info` resolves directly; isrc/mbid/duration from clients accrete onto entities. `playing_now` writes `polling_state` only for users without Spotify tokens (same rule as Last.fm). Plays are tagged `source='listenbrainz'`; scrobble-vs-polling twins are cleaned by the boot + daily dedup pair.

## Code style

- Comments in Spanish, technical terms in English
- No magic numbers — constants in `packages/api/src/constants.ts`
- Run `pnpm check` before committing: Vite only transpiles types, so nothing else catches type errors in `packages/web`. The web gate is `--threshold warning` and the tree is at 0/0 — a11y and unused-CSS warnings block too. Where a mouse-only handler is a deliberate enhancement over already-accessible content, suppress with `<!-- svelte-ignore <code>, <code> -->` (comma-separated) plus a comment saying why.
- `pnpm check` runs oxlint first (`.oxlintrc.json`, tree at 0 findings). Only `correctness` is on plus a few hand-picked rules; the `perf`/`suspicious` categories are off on purpose (they flag the deliberate sequential `await`s in Spotify pagination). Two rules are disabled for `.svelte` only, because the Svelte compiler defeats them: `no-unassigned-vars` (`bind:this` targets are assigned by the compiler) and `no-unused-expressions` (a bare `store.value;` inside `$effect` is how a dependency is registered — deleting it silently breaks reactivity).
- **Design tokens** (`app.css` `:root`, refresh of 2026-09-25): font sizes come from the scale (`--fs-2xs` … `--fs-3xl`, `--fs-display` for hero names), letter-spacing from `--track-tight/--track/--track-wide`, accent tints from `--accent-a05…a40` (never a hand-written `rgba(29,185,84,…)`), reds from `--danger`/`--negative`, the liked heart from `--like`. Only ECharts colors in JS stay literal (canvas can't read CSS vars). **Green is a signal, not decoration**: active state, primary actions, live, rank highlights, deltas and a page's single headline figure; numbers and values render in `--text`. Headings: section titles are `.section-title` (mono uppercase), group labels are mono `--fs-xs` muted with wide tracking, entity names and row content stay sans.
- Svelte 5 runes ($state, $derived, $effect)
- ECharts tree-shaken imports via echarts/core
- ECharts HTML tooltips: echarts sets `white-space:nowrap` **inline** on the tooltip element, so a class rule (via `className`) can't override it silently. Style the box through `tooltip.extraCssText` (appended to that same inline style) — see `RankingBadges.svelte`

## Git & deploy workflow

- Auto-commit is authorized in this repo (overrides the global "don't commit unless prompted" rule). Commit committable changes **before the turn ends**, grouped logically, with descriptive conventional-commit messages (`type(scope): summary` — feat/fix/chore, matching git history).
- Deploy is automatic: a `Stop` hook in `.claude/settings.local.json` (gitignored) runs `docker compose up --build -d` after the turn, but **only when `packages/**` changed** since the last deploy (marker: `.git/sis-last-deploy`). Committing packages changes is enough — don't deploy manually. A shell hook can't write descriptive commit messages, so the commit is done in-turn (by the agent), the deploy by the hook.
- Each deploy recreates the single container → a brief (~seconds) 502 while it restarts. Expected.
- **Store pipelines** (`.github/workflows/android-release.yml` + `ios-release.yml`, thin callers over the reusable workflows in the platform repo, same setup as duckhunt): every push to main that touches `packages/web`, `platform` or the workflows builds the `.aab` and the `.ipa`. iOS uploads to TestFlight on every push (app record "sis.fm" 6814445413, bundle `info.mier.sis`, profile "sis App Store CI"; the 7 signing secrets are in the repo, the material in gitignored `assets/ios-signing/`, shared cert/API key with duckhunt). Android uploads to Play **only when the repo variable `ANDROID_PLAY_UPLOAD` is `true`**: Play refuses API uploads until an app has one manual release, so the gate lives in a variable instead of a commit. `marketing_version` for iOS is declared once in the caller (`1.0.0`); bump it there when App Store Connect closes the train. Apple only takes digits, so the `26wNNx` snapshot never reaches iOS. `ios/` is not committed: the workflow scaffolds it with `cap add ios` each run.
- No changelog: the app ships no release notes. The version tag in the sidebar footer is plain text; don't reintroduce a changelog file, route or modal.
- **The submodule pointer and `pnpm-lock.yaml` move in the same commit.** `pnpm-workspace.yaml` globs `platform/packages/*`, so the root lockfile's `importers:` map is a function of the *pinned* platform commit, not of your local submodule working tree. One importer too many or too few and CI's `pnpm install --frozen-lockfile` dies before any build step: `packages/changelog` broke every push to main from 2026-08-31 to 2026-09-14 (10 runs) because its deletion was committed in sis but never pushed to platform, with `packages/oidc-rp` queued behind it (pnpm reports only the first mismatch). Never commit a lockfile regenerated against uncommitted submodule changes. The pnpm version comes from the root **`packageManager`** field (`pnpm@11.26.0`): platform's reusable workflows deliberately pass no `version:` to `pnpm/action-setup`, so CI reads that same field and cannot drift from local. It used to pin pnpm 9 against a local 11, with the lockfile written by one and validated by the other. Bump the field and your local pnpm together, and never also pass a `version:` input, since declaring both with different values kills the action outright.
